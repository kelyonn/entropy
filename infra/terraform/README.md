# Entropy AWS data plane

This stack creates the production VPC, EKS cluster, PostgreSQL, Redis, S3,
Cognito, IAM roles, runtime secrets, ECR repositories, and CloudWatch alarms.

**Operator runbook:** see [`docs/your-actions.md`](../../docs/your-actions.md)
for credentials, DNS/ACM, apply, EKS deploy, and Amplify steps.

## State and apply

Create an S3 state bucket and DynamoDB lock table once, then initialize:

```sh
terraform init -reconfigure \
  -backend-config="bucket=<state-bucket>" \
  -backend-config="key=entropy/production.tfstate" \
  -backend-config="region=us-east-1" \
  -backend-config="dynamodb_table=<lock-table>"
terraform plan -out=entropy.tfplan
terraform apply entropy.tfplan
```

Optional: `-var='alarm_email=you@example.com'` for SNS email alerts (confirm the
subscription).

Database and Redis credentials are generated by Terraform and stored in
Secrets Manager. Do not place them in tfvars or Kubernetes manifests.

## Airlock node requirement

Airlock uses the Docker Engine API to create a nested sandbox container. The
EKS worker launch template installs and starts Docker alongside the EKS
container runtime. The Airlock pod is the only workload that may mount
`/var/run/docker.sock`; its node placement, service account, and network policy
must remain restricted. This grants node-level control and is a deliberate
design constraint, not a general workload pattern.

## Smoke checks

After apply and deployment:

1. Run a temporary pod with the Session Manager service account.
2. Read the DB and Redis URLs from the `entropy-secrets` Kubernetes secret.
3. Run `pg_isready` against the RDS endpoint.
4. Run `redis-cli --tls -u "$REDIS_URL" ping`.
5. Upload and download a test object in the snapshot bucket.
6. Delete the temporary pod and test object.
